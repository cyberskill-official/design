# Anchored floating panels

The following components render their anchored panel in a body portal by default: Tooltip, Popover, HoverCard, Popconfirm, Menu, ContextMenu, Combobox, DatePicker, Cascader, TreeSelect, ColorPicker, Mentions, Menubar, NavigationMenu, Toolbar, FloatingActionButton, AIDisclosureBadge. Inside an original inline insertion parent belonging to a native `form` or `fieldset`, placement automatically stays local even with `portal={true}`. Set `portal={false}` for explicit inline rendering. Modal dialogs, drawers, image previews, toast viewports and inline editors retain their separate contracts.

`placement` accepts `top`, `bottom`, `left`, `right` and each side with `-start` or `-end`. Sides are physical; top/bottom start and end follow the anchor's text direction. The panel flips when the opposite side has more usable space, shifts inside the visual viewport and follows ancestor scrolling, resize and visual viewport events. Existing alignment props still choose their corresponding placement when `placement` is omitted. Tooltip defaults to top, floating actions to top-end, toolbar overflow to bottom-end, and other panels to bottom-start.

Portals preserve React context, scoped messages, computed custom properties, font/color and explicit theme, language, direction, density and contrast axes. Source ancestor hidden, inert and aria-hidden controls remain effective. CSS selectors that require a particular source ancestor do not cross a portal; use explicit scope tokens or `portal={false}` when that ancestry is required. Inline panels remain subject to ancestor clipping and stacking contexts.

The existing overlay manager registers the actual panel and its logical parent. Nested panels remain inside parent focus and dismissal scopes. Interactive panels retain logical keyboard traversal beside their trigger even though their physical DOM is under the body. Component-owned menu keyboard contracts still apply. A body portal is not a modal and does not add a focus trap.

Server rendering and the first hydration render omit body-portaled panel content; the client mounts it after the portal host exists. `portal={false}` retains inline server markup. Panel refs are null while their element is absent; wrapper and control refs keep their documented targets. Changing `portal` remounts floating children and resets their local state, while the owning component and trigger remain mounted. Keep the mode stable when child state must persist.

The helper uses existing inline style attributes for geometry and scope inheritance. Script CSP hardening does not imply a style CSP change. Browser tests cover all 17 owners, inline and body modes, nested modal ownership, physical placement/RTL, clipping, scroll/resize, logical Tab order, scoped context and mode remounts. Synthetic visual viewport resize evidence does not claim physical mobile keyboard acceptance.

During an open session, the positioning helper owns constrained placement and may clamp caller sizing to the available viewport. It tracks its last geometry writes separately from subsequent caller writes, including their CSS priority. Closing or unmounting restores the latest caller geometry values rather than an earlier snapshot. Natural-size measurement preserves the panel's current horizontal and vertical scroll offsets, subject to the final available scroll range; scrolling or focusing later content must remain usable after repositioning. This does not add a panel style prop or change the documented native ref target.

Automatic native-form fallback preserves the original insertion ancestry through the same private `display: contents` portal host. It retains native form ownership, `form.elements`, `FormData`, reset, validation, submitters and disabled-fieldset/first-legend semantics. It does not infer serialization or form ownership from the opener: a ContextMenu whose zone wraps a descendant form still places its menu outside that descendant form. Local fallback is subject to ancestor clipping. The existing panel classes and overlay ownership remain intact; the private host adds a DOM level, so direct-child consumer CSS should use the actual panel class or explicit inline rendering when exact markup is required.

The host follows source ancestor insertion and movement after MutationObserver delivery. Automatic local/body changes keep the same child React tree and DOM nodes, preserving entered state and native refs. State-preserving DOM movement is used where available; otherwise the helper restores the previously focused descendant and selection when possible. Native focus/blur events are not suppressed, and a caller that closes or removes content in response can prevent restoration. Native disabling correctly prevents focus restoration into disabled controls. Explicit changes to the `portal` prop retain the documented child-remount behavior.

Requested portals, including automatic local fallback, remain absent from SSR and the first hydration render; their first client mount already uses the detected native ancestry. Use explicit `portal={false}` when open panel controls must exist in server markup. Observer delivery is asynchronous: moving a source and immediately submitting, reading `FormData`, or explicitly blurring in the same task is not an atomic compatibility guarantee. Keep the source in its native context before opening/submitting, use explicit inline rendering for synchronous movement, or await the next settled browser update.
